# Contact Transaction App — Contact Service

`CONTACT-SERVICE` is the Contact module of the Contact Transaction App. It is a
learning project built with Java 24, Spring Boot, Maven, Oracle Database, and
Spring Cloud Netflix Eureka.

The service logically owns `SYSTEM.CONTACT` in the current training database.
It must not read User Service or Money Service tables directly.

## Current status

Implemented:

- Oracle `CONTACT` entity and owner-scoped repository
- Real Oracle persistence tests
- Create, list, get, update, and delete service operations
- User Service client through Eureka service ID `USER-SERVICE`
- Contact request validation and response mapping
- Safe exception responses
- Trace-ID propagation through headers, error bodies, and logs
- Eureka client configuration
- JWT validation with the User Service public key
- Authenticated owner extraction from JWT `sub`
- Public owner-scoped Contact REST endpoints

Still deferred:

- API Gateway route
- Live Eureka registration verification

The Contact API never accepts `owner_user_id` from a public header, query
parameter, or request body. It obtains the owner only from the signed JWT.

The service uses one configuration file:

```text

```

Required environment variables:

| Variable | Purpose |
| --- | --- |
| `DB_URL` | Oracle JDBC URL |
| `DB_USERNAME` | Oracle username (`SYSTEM` in the current training setup) |
| `DB_PASSWORD` | Password for the configured Oracle username |
| `EUREKA_URL` | Eureka server URL |
| `USER_SERVICE_INTERNAL_TOKEN` | Shared token for internal User Service calls |

Use `.env.example` only as a reference. Spring Boot does not automatically load
that file, and real credentials must not be committed.

The default local JDBC URL is:

```text
jdbc:oracle:thin:@//localhost:1521/FREE
```

The current training setup stores the application tables under the privileged
`SYSTEM` schema in the `FREE` root database. This is not recommended for a
production application, but it is the explicitly selected demo layout.

In an IntelliJ run configuration, add the variables under:

```text
Run → Edit Configurations → Environment variables
```

## Manual Oracle setup

Flyway is intentionally not used. Connect to service `FREE` as `SYSTEM` and run
the authoritative contact DDL below. Do not store the SYSTEM password in the
repository.

```sql
CREATE TABLE contact (
    contact_id      NUMBER GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    owner_user_id   NUMBER NOT NULL,
    linked_user_id  NUMBER,

    contact_name    VARCHAR2(20 CHAR) NOT NULL,
    contact_phone   NUMBER(10) NOT NULL,

    created_at      TIMESTAMP DEFAULT SYSTIMESTAMP NOT NULL,
    updated_at      TIMESTAMP DEFAULT SYSTIMESTAMP NOT NULL,

    CONSTRAINT pk_contact PRIMARY KEY (contact_id),

    CONSTRAINT ck_contact_not_self
        CHECK (
            linked_user_id IS NULL
            OR linked_user_id <> owner_user_id
        )
);

CREATE INDEX ix_contact_owner ON contact (owner_user_id);
CREATE INDEX ix_contact_linked ON contact (linked_user_id);

CREATE OR REPLACE TRIGGER trg_contact_bu
BEFORE UPDATE ON contact
FOR EACH ROW
BEGIN
    :NEW.updated_at := SYSTIMESTAMP;
END;
/
```

The service uses `spring.jpa.hibernate.ddl-auto=validate`. Hibernate verifies
the mapping but does not create or alter the schema.

There are no database foreign keys from `SYSTEM.CONTACT` to User Service
tables. `owner_user_id` and `linked_user_id` remain external User Service
identifiers even though the training database physically shares one schema.
Service ownership is enforced in application design rather than by separate
Oracle credentials in this demo.

Oracle owns identity generation and both timestamp defaults. The update trigger
owns `updated_at`; application update code does not assign it.

## User Service integration

Calls use the Eureka service ID:

```text
http://USER-SERVICE
```

Current internal contracts:

```http
GET /internal/v1/users/{userId}/status
```

```json
{
  "userId": 101,
  "status": "ACTIVE"
}
```

```http
POST /internal/v1/users/resolve
```

```json
{
  "mobileNo": "9876543210"
}
```

```json
{
  "userId": 101,
  "status": "ACTIVE"
}
```

The client sends `USER_SERVICE_INTERNAL_TOKEN` in
`X-Internal-Service-Token`, matching the User Service internal-token filter.

The client uses a 2-second connection timeout and a 3-second response timeout.
If User Service cannot validate a requested link, Contact Service raises a safe
`503 Service Unavailable` response and does not silently create the link.

Because Kafka is excluded, this service does not automatically receive later
user-deactivation events. Operations that depend on an active linked user must
validate the current User Service status synchronously.

## Validation and database limitations

- Contact names are trimmed and must contain 2–20 characters.
- Contact phone input must be a JSON string containing exactly ten digits.
- The validated phone is converted to `Long` for Oracle `NUMBER(10)` storage.
- Numeric storage cannot preserve leading zeroes. For example, `"0123456789"`
  is stored numerically as `123456789` and cannot be reconstructed exactly.
- The schema is authoritative and is not changed to solve this limitation.
- Self-linking is rejected in the service and by `CK_CONTACT_NOT_SELF`.
- The table has no `version_no`, so JPA optimistic locking is not implemented.

## Authentication status

Contact Service validates User Service RS256 access tokens using `JWT_PUBLIC_KEY`.
Every `/api/v1/contacts/**` request requires a valid token whose numeric `sub`
claim becomes the owner ID. The health endpoint remains public.

## Eureka

The service registers under:

```text
CONTACT-SERVICE
```

Default Eureka configuration:

```properties
eureka.client.serviceUrl.defaultZone=${EUREKA_URL:http://localhost:8761/eureka/}
```

Modern Spring Cloud enables discovery through the starter dependency; an
`@EnableEurekaClient` annotation is not required. Live registration can be
verified only while a Eureka Server is running.

The required Gateway route is:

```text
/api/v1/contacts/** → lb://CONTACT-SERVICE
```

No `/internal/**` Contact Service route should be exposed publicly.

## Trace IDs and safe logging

The service accepts a safe `X-Trace-Id` header or generates a UUID. The same ID
is added to response headers, error bodies, and safe logs.

Logs contain only appropriate operational fields such as request path, status,
trace ID, duration, and error code. Request bodies, JWTs, internal tokens,
passwords, database credentials, and sensitive exception details are excluded.

## Build and tests

Preferred Maven Wrapper command:

```powershell
.\mvnw.cmd test
```

The Windows wrapper's generated PowerShell symlink check was repaired and the
wrapper has been verified with Maven 3.9.16 and Java 24.0.2. A compatible global
Maven installation is optional; normal project commands should use the wrapper.

Oracle tests run only when `DB_USERNAME` and `DB_PASSWORD` are present. Supply
all required values as temporary environment variables or through the IntelliJ
Maven run configuration.

After changing the training database location to `FREE/SYSTEM`, the latest
credential-free verification produced:

```text
Tests run: 51, Failures: 0, Errors: 0, Skipped: 4
BUILD SUCCESS
```

The four skipped tests are the real Oracle persistence tests. Run again with
the local SYSTEM credentials to verify `SYSTEM.CONTACT`.

Before a final release, run:

```powershell
.\mvnw.cmd clean verify
```
